## How it works

- **Default is English.** The language is a per-device setting stored under the device-local key
  `mrchartist_inv_lang` (`LANG_KEY` in `storage.ts`, listed in `DEVICE_LOCAL_KEYS`): it stays in localStorage, is readable
  before unlock (so the PIN and vault screens are translated), is ignored by cross-tab "data changed" notices and is
  **never written to or restored from a backup**. Another tab switching language is followed via the `storage` event.
- **Boot.** `main.tsx` awaits `initI18n()` alongside `initStorage()`; for a Hindi device that imports the Hindi chunk
  before the first render, so nothing flashes in English. `public/theme-init.js` sets `<html lang>` even earlier;
  `setLanguage` keeps it in sync.
- **English users pay ~3.7 kB gz** of first-paint JS (the shell catalogue and the i18n helpers, measured 173.6 →
  177.3 kB against the 185 kB budget); the Hindi catalogue is never downloaded for them.
- **Fallback.** `t()` looks in the active catalogue, then English, so an untranslated key shows English, never the key.
  The Hindi catalogue is typed `Messages`, so a missing key fails `npm run typecheck`; the test suite also checks that
  every key has the same `{placeholders}` in both languages.
- **Numbers stay Latin with Indian grouping** in both languages (`formatCurrency` stays `en-IN`): amounts are compared
  against bank statements, the GST portal and Tally, which all use them. Dates written in words on the Dashboard use
  `hi-IN-u-nu-latn` (Hindi month / weekday names, Latin digits); document dates are unchanged.
- **Stored values stay English.** Document types, statuses, payment methods and roles are saved in English (they are
  data, printed on receipts and exported); only their on-screen label is translated through `labels.ts`.

## Documents

- The existing **Bilingual (Hindi)** template prints English labels with a Hindi line under each one, and now the amount
  in words in both languages: "Amount in words: Rupees Twelve Crore … Only" + "रुपये बारह करोड़ … और पाँच पैसे मात्र".
  It is a template like any other: it keeps the `--tpl-accent` variable and reads the document's own sender snapshot.
- Printed documents do **not** follow the interface language: a Hindi-speaking user can still issue English invoices,
  and an English UI can issue bilingual ones. With the Hindi UI, the editor's summary also shows the Hindi amount in words.
- `amountInWordsHi` uses the Indian system for every currency (सौ, हज़ार, लाख, करोड़; crores above 99 recurse: "एक सौ
  बीस करोड़"), rounds to paise first, writes "ऋण" for negatives and "शून्य" for zero.

## Devanagari font (fixes PDFs that differed by device)

PDFs are screenshots of the page (`html-to-image`), so Hindi used to render in whatever Devanagari font the device had
(Mangal, Kohinoor, Noto, none…). Now:

- `Noto Sans Devanagari` (SIL OFL 1.1, Devanagari subset from the `@fontsource/noto-sans-devanagari` 5.3.0 package,
  weights 400 and 700, ~50 kB each) is self-hosted under `/fonts` and precached by `sw.js` like every other font.
- Its `unicode-range` is Devanagari only (U+0900–097F, Vedic extensions, ZWJ/ZWNJ) — not ₹ or Latin — so it downloads
  only when a page shows Hindi text, and Latin glyphs keep the template's own font.
- It leads every font stack (`--font-devanagari` at the front of `--font-body`, `--font-display`, `--font-serif`,
  `--font-mono`, `--font-accent`, and in `TemplateEngine` for Design Studio font overrides), so Hindi item names and
  addresses also use it in every template.
- Before capturing a PDF, `ensureDevanagariFont()` waits for both weights when the page contains Devanagari.

To update the font: `npm pack @fontsource/noto-sans-devanagari` in a scratch folder, copy
`files/noto-sans-devanagari-devanagari-{400,700}-normal.woff2` to the names above, and keep the licence file.

## Adding or changing strings

1. Add the English text to `src/i18n/en.ts` if the shell / login / vault / Dashboard needs it, otherwise to
   `src/i18n/en-pages.ts`. Keys are `area.name`; placeholders are `{name}`. Pass amounts already formatted.
2. Add the Hindi text with the same key and placeholders to `src/i18n/hi.ts` (typecheck fails until you do).
3. In a component: `const { t } = useT();` then `t('area.name', { n })`. Use `tNodes` when a placeholder is a React
   node (`<strong>`, `<kbd>`, a countdown) so each language keeps its own word order. Plurals: two keys
   (`…One` / `…Many`).
4. A module that uses an `en-pages` key must `import '…/i18n/en-pages';` (a test enforces it), so its English text is
   registered before it renders.
5. Keep accessible names stable for tests where possible; the e2e journey runs in English except for its language step.
6. Never translate statutory wording you are not sure about: keep the English, including "verify with your CA".

## Per-area catalogues (round 2)

Screens translated after the first round keep their strings in `src/i18n/areas/<area>.ts`, made with
`defineArea(en, hi)` from `src/i18n/area.ts`: English and Hindi side by side, Hindi type-checked for every key, and
`tests/i18n-areas.test.ts` checks placeholders. An area file is imported only by its (lazy) screens, so it never
reaches first paint and areas can be translated in parallel without touching `en.ts` / `en-pages.ts` / `hi.ts`.
Components call `useT()` (to re-render on a language switch) and the area translator, e.g. `gstT('title')`.
